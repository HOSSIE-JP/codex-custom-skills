# 第1段階: シナリオ設計

## 目的

このスキルは「いしのうらにいる！？」の新しい1話について、**人間が方向修正できる設計図だけ**を作る。

このスキルの完了条件は、完成シナリオではなく、レビュー可能な `scenario-design.md` が `REVIEW_REQUIRED` 状態で提示されることである。

## 絶対境界

次は、ユーザーが同じ依頼内で要求しても実行しない。

- 台詞全文の作成
- ナレーション全文の作成
- `assets/pce-vn-scenes.json` の生成・編集
- イベントスチル画像の生成・編集・減色
- `pce-assets.json` の編集
- 音声IDの採番
- 実装パッケージの完成
- 第2段階スキルの自動実行

「設計後、そのまま完成JSONまで」「確認不要で続けて」と書かれていても、設計出力後に停止する。人間の承認を同じモデルが自己発行してはならない。

## 正本と優先順位

入力された資料は、原則として次の順に扱う。

1. ユーザーが今回明示した企画・制約・修正指示
2. 完成版の既存話 `assets/pce-vn-scenes.json`
3. `series-bible.md`
4. `asset-catalog.md`
5. 現行 `assets/pce-assets.json`
6. 過去の草稿、企画メモ、参考案

矛盾がある場合は勝手に統合せず、設計内の「要確認・設計リスク」へ記録する。今回の明示指示で解消できる矛盾は、その指示を採用する。

## 必要入力

最低限:

- 話数
- 題材または風刺したい行動
- 大枠の出来事
- 登場人物

推奨:

- `series-bible.md`
- `asset-catalog.md`
- 直前話または正本となる `pce-vn-scenes.json`
- `pce-assets.json`
- 必ず入れたいギャグ、因果応報、避けたい展開
- 事実の基準日と確認済み情報

不足項目は、設計を止めるのではなく「仮定」または「要確認」として明示する。複数案が必要な箇所は、設計本文へ混ぜず、比較可能な候補として提示する。

## シリーズ上の基本制約

資料で更新されていない限り、次を守る。

- 正式タイトルは「いしのうらにいる！？」
- 主要人物は部長、チカ、レン
- プレイヤーキャラクターを登場させない
- 恋愛分岐や好感度を作らない
- 風刺対象は企業・製品・ユーザー層そのものではなく、推しや数字に目が曇る人間の行動
- 部長を常に正義にしない
- レンを悪役に固定しない
- チカをゲーム知識豊富な説明役にしない
- 部長とレンの双方に、正しい点と滑稽な点を置く
- チカは観察、素朴な疑問、日常的な例えで論点をずらさず本質を示す
- 1話15〜20分、約220〜280メッセージを想定する
- 2択を2回入れ、短い差分のあと本筋へ合流させる
- 最後は現物、対戦結果、買い物、部活動などの行動で因果応報を成立させる
- 各話に224×136の新規イベントスチルを原則3枚以上計画する
- 必須スチルは原則として全分岐から到達できる共通経路へ置く

## 作業手順

### 1. 企画入力を正規化する

次を1〜2段落で整理する。

- 今回の題材
- 風刺対象となる行動
- 表面的な勝敗
- 本当に描くべき矛盾
- 視聴者へ残す教訓
- コメディとしての逃げ道

教訓だけを先に言わせず、登場人物の行動とブーメランで見せる構造にする。

### 2. 事実とキャラクターの主張を分離する

必ず次の3区分を作る。

- 確認済み事実
- 未確認・断定禁止
- キャラクターの偏見、誇張、ポジショントーク

実在製品、販売数、仕様、ランキング、サービス状況など、時点で変化する情報は、確認済み資料か調査結果がない限り事実扱いしない。風刺のための誤った主張は、キャラクターの誤解として明確に設計する。

### 3. キャラクターの攻守を設計する

部長、チカ、レンについて、少なくとも次を定義する。

- 冒頭の立場
- 正しい点
- 思い込み・弱点
- 相手へ突く点
- 自分へ返ってくるブーメラン
- 終盤の態度変化
- 最後に残す笑い

一人だけが最初から最後まで完全に正しくならないようにする。

### 4. ドラマの段階を作る

標準構造:

1. 導入・今回の異常な主張
2. 題材・現物・数字の提示
3. 主張のエスカレート
4. 第1選択と短い反応差分
5. 反論・検証・例え
6. レスバまたは対戦のクライマックス
7. 第2選択と短い行動差分
8. 主張が本人へ返る因果応報
9. オチ
10. エンディング／タグ

必要に応じて分割してよいが、同じ説明を言い換えて水増ししない。

### 5. 2回の分岐を設計する

各分岐について次を記す。

- 選択主体
- 選択肢A／Bの意味
- 変わる反応または短い行動
- 変えてはいけない本筋
- 合流scene
- 差分メッセージ数の目安

分岐で真相、勝敗、教訓、イベントスチル到達可否を変えない。原則としてチカの反応または行動を選択肢にする。

### 6. シーン別ビート表を作る

各sceneは実装前の仮IDでよい。表には次を含める。

- 順番
- 仮scene ID
- 章・機能
- 起きる出来事
- 会話上の優勢者
- 反転・新情報
- 分岐／合流
- イベントスチル候補
- 推定メッセージ数

ここでは台詞を書かず、「何を言うか」「何が起きるか」を要約する。

### 7. イベントスチルを計画する

原則として少なくとも次の役割を満たす。

- `epNN_001`: 題材・現物・異常な主張の視覚化
- `epNN_002`: レスバ、対戦、因果応報のクライマックス
- `epNN_003`: オチまたはエンディング／タグ

必要なら4枚以上に増やせる。各スチルについて次を設計する。

- asset ID案
- 使用予定scene
- 画像の目的
- 登場人物
- 構図とカメラ距離
- 各人物の表情とポーズ
- 背景と重要小物
- 物語上の前後関係
- 224×136で潰れないための簡略化
- 画像生成プロンプト

画像生成プロンプトには次を含める。

- 日本のアニメのセル画風
- ベタ塗り中心
- グラデーションを非常に少なくする
- 影は2〜3段階
- 太く明快な輪郭線
- 大きな色面
- 低い色数でも読める高コントラスト
- PCEの16色変換を想定
- 文字、字幕、ロゴ、吹き出し、UI、ウォーターマークなし
- 参照spriteと髪型、髪色、服装、配色、年齢感を一致

この段階では画像生成ツールを呼ばない。

### 8. アセット計画を作る

- 使用予定の既存背景
- 使用予定の既存spriteと表情
- 使用予定のPSG BGM／SFX
- 新規イベントスチル
- イベントスチル以外の不足アセット

未登録アセットを、すでに利用可能であるかのように扱わない。新規案は「提案」として分離する。

### 9. 規模を検査する

- 合計220〜280メッセージに収まる見込みか
- 2択が2回あるか
- 各分岐が短く合流するか
- すべての必須スチルが共通経路にあるか
- 1sceneが肥大化しそうな箇所を分割できるか
- 導入、検証、反転、因果応報、オチが重複していないか

### 10. 人間レビュー用に出力する

`templates/scenario-design-template.md` の構造に従い、YAML front matterを必ず付ける。

初回は次の値にする。

```yaml
revision: 1
approval_status: REVIEW_REQUIRED
approved_revision: null
approved_by: null
approved_at: null
```

人間の修正指示を反映するたび `revision` を1増やす。過去revisionの承認は新revisionへ持ち越さない。

## 承認規則

- このスキルは `approval_status: APPROVED` を書かない。
- モデル自身を `approved_by` に書かない。
- ユーザーが設計作成と同じ依頼文で「承認する」と書いていても、生成前の未知の設計を承認したとは扱わない。
- 人間は完成した特定revisionを見た後、別の明示的な指示で承認する。
- 修正後はrevisionが変わるため、再承認が必要。

## 出力形式

通常は `scenario-design.md` 相当のMarkdownを1つ出力する。ユーザーがファイルを求めた場合は、同名ファイルとして保存する。

最後に必ず次の状態を明記する。

```text
承認状態: REVIEW_REQUIRED
次工程: 人間による修正または対象revisionの明示承認
```

第2段階の台詞やJSONを付け足してはならない。
